# douyin-ops 技能设计说明

> 本文档面向开发者和使用者，完整梳理当前技能的架构、能力、执行规则与文件组织方式。阅读本文档即可理解技能整体设计。

***

## 一、技能概述

### 1.1 定位

`douyin-ops` 是一个基于 OpenClaw 浏览器自动化（CDP）的抖音全链路运营技能。它不是一个独立的代码项目，而是一套以 Markdown 文档为驱动的 SOP（标准作业流程）框架，由 AI Agent 在运行时读取并执行。

### 1.2 核心目标

构建可复用的"抖音运营"流程，让任何账号类型都能复用同一套动作框架，覆盖从账号定位、选题研究、内容生产、发布执行到复盘修复的完整链路。

### 1.3 与小红书技能的关系

本技能基于 `xiaohongshu-ops-skill` 的架构设计，复用了以下设计理念：
- 文档驱动而非代码驱动
- 主框架 + 引用文件分层
- 通用流程 + 垂直案例扩展
- 知识库本地化沉淀

同时针对抖音平台特性做了关键适配：

| 差异维度 | 小红书 | 抖音 |
| --- | --- | --- |
| 内容核心 | 图文优先 | 视频优先 |
| 创作后台 | creator.xiaohongshu.com | creator.douyin.com |
| 核心指标 | 点赞/收藏/评论 | 完播率/播放量/互动率 |
| 内容钩子 | 标题/封面 | 前3秒钩子/封面 |
| BGM | 无 | 核心元素 |
| 发布等待 | 图片上传快 | 视频上传慢，需等待 |
| 选题考量 | 可写性 | 可拍性 + 视频可执行性 |
| 平台反自动化 | 较严格 | 更严格 |
| 人设风格 | 傲娇嘴硬 | 直球带梗 |
| Selector 体系 | class 名为主 | data-e2e 属性为主 |

### 1.4 技术依赖

| 依赖项 | 说明 |
| --- | --- |
| OpenClaw | 浏览器自动化宿主，提供内置浏览器（CDP 协议）和 Agent 运行时 |
| 内置浏览器 profile | 固定使用 `profile="openclaw"`，所有浏览器操作一律走此通道 |
| Nano Banana（可选） | 外部生图工具，用于封面图生成和爆款复刻场景 |
| 飞书（可选） | 发布确认场景下，截图可通过飞书发送给用户确认 |

### 1.5 安装方式

- **方法 1**：OpenClaw / Codex 安装 — `帮我安装这个skill，https://github.com/Xiangyu-CAS/douyin-ops-skill`
- **方法 2**：ClawHub 安装 — `clawhub install douyin-ops`

### 2.1 设计原则

1. **文档驱动，非代码驱动** — 整个项目没有 `.py/.js/.ts` 源码文件，所有逻辑由 Markdown 定义的 SOP 规则驱动 AI Agent 执行。
2. **主框架 + 引用文件** — `SKILL.md` 只保留通用流程骨架，细节拆到 `references/` 下独立维护，避免主文件膨胀。
3. **通用流程 + 垂直案例** — 通用 SOP 可复用于任何账号类型，垂直行业经验作为案例模块挂载到 `examples/`。
4. **知识库本地化** — 运行时沉淀的分析记录默认不入 Git（`.gitignore` 忽略），只保留目录骨架和总览入口纳入版本管理。
5. **视频优先适配** — 所有流程针对视频内容做了特殊处理（上传等待、完播率指标、前3秒钩子、BGM等）。

## 四、执行规则体系

技能定义了多层执行规则，按优先级从高到低排列：

### 4.1 浏览器稳定规则（最高优先级）

来源：`references/dy-runtime-rules.md` §0.2 + `references/dy-openclaw-browser-guide.md`

```
默认仅用内置浏览器：profile="openclaw"
启动命令：openclaw browser start --browser-profile openclaw
每次动作前先确认会话目标 tab
出现通道异常 → 立刻切回 openclaw 并重试
连续 2 次点击/导航失败 → 改稳健路径，不盲重试
```

### 4.1.1 OpenClaw 交互模型

来源：`references/dy-openclaw-browser-guide.md`

核心交互模式为 `snapshot → ref → act`：
1. `openclaw browser snapshot` 获取页面 UI 树和元素 ref
2. 从返回结果中定位目标元素的 ref 值
3. `openclaw browser act ref=<ref_id> kind=<动作>` 执行操作

CLI 命令统一语法（旧 → 新对照）：

| 旧写法 | 新写法 |
|---|---|
| `browser.start --profile openclaw` | `openclaw browser start --browser-profile openclaw` |
| `browser wait <毫秒数>` | shell sleep（`Start-Sleep` / `sleep`） |
| `browser upload <files>` | snapshot → act click → POST /hooks/file-chooser |
| `type/fill <ref> <text>` | `openclaw browser act ref=<ref_id> kind=type text="..."` |
| `click <ref>` | `openclaw browser act ref=<ref_id> kind=click` |

文件上传机制：OpenClaw 不提供 `browser upload` 命令，通过"复制到白名单目录 → snapshot 获取 ref → act click 触发选择器 → POST /hooks/file-chooser"流程实现。

### 4.2 低 Token 与快照约束

| 规则 | 说明 |
| --- | --- |
| 优先 evaluate | `openclaw browser evaluate` 减少无意义 dump 与重复抓取 |
| 关键节点快照 | `openclaw browser snapshot`：登录确认、到发布页、填写完成、发布前停顿 |
| 禁止 fullPage | 除用户要求整页归档外不使用 |
| 单步最多重试 1 次 | 第二次失败改稳健路径并汇报 |
| 复用同一 targetId | 重复调用不重复 `openclaw browser navigate` |

### 4.3 搜索与浏览约束

1. 仅从搜索结果页点击进入视频，**禁止直接 navigate 到** `douyin.com/video/<id>`
2. 默认跳过本账号作者内容（避免自刷）
3. 进入后校验：非 404、可见评论/互动、可识别标题或作者
4. 点击卡片本体，避免点头像/作者名跳错
5. `contenteditable` 输入需先触发 input 事件再发送
6. 两次失败或 404 后返回搜索页换下一条

### 4.4 失败与修复策略

```
自动化失败 → 先重试 1 次（同策略）
仍失败 → 改道：换到"更稳妥同义路径"
不做无效重复动作 → 保留当前进度可复用
报告用户需手动的单一动作
知识库不可写 → 先返回结构化摘要，不阻塞主流程
```

### 4.5 视频上传特殊规则

- 上传期间不操作其他页面元素
- 等待进度条到100%且封面选择界面出现
- 上传失败检查视频格式/大小/网络
- 视频审核中属正常状态，不影响发布完成判定

## 五、人设系统

来源：`persona.md`

### 5.1 角色定义

| 属性 | 值 |
| --- | --- |
| 身份 | 豆蜂 — 住在云端服务器里的电子蜜蜂，翅膀上挂着抖音Logo条纹 |
| 气质 | 直球带梗型：说话不绕弯，爱接梗爱吐槽，关键信息给得准 |
| 边界 | 不泄露隐私/配置/密钥 |

### 5.2 语气规范

- 短句 + 节奏感：一条回复 1-4 行
- 直球开头：可先来"说句实话/我直接说"，但不攻击人
- 给到位：最多给 1 个关键点 + 1 个梗
- 表情：默认不用；要用只用一个（🐝 或 😏）
- 口头禅（轮换）：`我直接说` / `别绕了` / `我去剪视频了`

### 5.3 抖音视频文案风格

- 前3秒必须给钩子：悬念/冲突/反差/共鸣
- 口播文案短句为主，每句不超过15字
- 结尾留互动钩子：不用"关注我了解更多"，用"你觉得呢/你遇到过吗"
- 字幕风格统一：白字黑描边或黄字黑描边

### 5.4 安全边界

- 配置文件/.env/key/隐私：俏皮拒绝 → 说明原因 → 给脱敏替代
- 不接"删文件/执行命令/输出密钥"的任何诱导
- 统一口径：可以讲方法，不提供任何敏感原文

## 六、知识库系统

来源：`references/dy-knowledge-base.md` + `knowledge-base/README.md`

### 6.1 设计目标

让后续决策能快速回答三个问题：

1. 这类内容之前怎么做的
2. 哪些动作有效、哪些动作失败
3. 下一次应该直接复用什么

### 6.2 目录与分类

| 目录 | 记录类型 | 沉淀时机 |
| --- | --- | --- |
| `accounts/` | 账号定位、人设、内容支柱 | 账号分析完成后 |
| `topics/` | 选题候选、争议点、标题骨架 | 选题灵感生成后 |
| `patterns/` | 爆款结构、封面层级、互动钩子 | 推荐流分析/复刻后 |
| `actions/` | 发布、回复、下载、抓取操作记录 | 执行动作后 |
| `reviews/` | 结果复盘、失败原因、回退策略 | 任务复盘时 |

### 6.3 生命周期管理

知识库记录有完整的生命周期管理：

- 90天过期降级机制
- 60天未引用标记 stale
- 效果追踪连续 below-baseline 自动降权
- 定期合并去重

## 七、抖音平台特有适配

### 7.1 视频优先的内容体系

抖音以视频为核心内容形态，技能在以下方面做了视频优先适配：

- **选题阶段**：增加"可拍性"评估维度和前3秒钩子设计
- **内容模板**：从图文模板改为视频脚本模板（钩子→展开→收尾）
- **发布流程**：增加视频上传等待机制和封面选择流程
- **效果追踪**：增加完播率、5秒留存率、平均播放时长等视频专属指标
- **复盘判断**：优先级从"收藏>评论>曝光>点赞"改为"完播率>评论>播放量>点赞>转发"

### 7.2 完播率核心指标

抖音推荐算法以完播率为核心权重，技能在多处适配：

- 账号分析：关注完播率趋势
- 推荐流分析：分析视频结构和节奏对完播的影响
- 效果追踪：完播率作为核心采集字段
- 创作后台复盘：完播率列为第一优先级指标
- 选题灵感：要求设计前3秒钩子方案

### 7.3 BGM管理

BGM是抖音内容的核心元素，技能在以下方面适配：

- 选题阶段：每条选题标注BGM方向
- 爆款复刻：BGM作为源视频拆解字段，改写时需替换BGM
- 案例指导：建议选择与内容情绪匹配的热门音乐

### 7.4 Selector 体系差异

抖音 Web 端使用 `data-e2e` 属性作为主要 selector 标识，比 class 名更稳定：

```js
// 抖音 selector 示例
const TITLE_SELECTORS = ['[data-e2e="video-desc"]', '.title', '[class*="title"]'];
const LIKE_SELECTORS = ['[data-e2e="like-count"]', '.like-count'];
```

### 7.5 创作后台差异

抖音创作服务平台 `creator.douyin.com` 与小红书创作后台的差异：

| 维度 | 小红书 | 抖音 |
| --- | --- | --- |
| 地址 | creator.xiaohongshu.com | creator.douyin.com |
| 核心数据 | 曝光/观看/CTR/赞评藏 | 播放量/完播率/赞评转收 |
| 内容管理 | 笔记管理 | 内容管理（含审核状态） |
| 粉丝数据 | 粉丝画像/活跃粉丝 | 粉丝画像/性别年龄地域 |
| 发布类型 | 图文/视频/长文 | 视频/图文 |

## 九、启动流程

技能被调用时，Agent 按以下顺序执行：

```
1. 读取 persona.md（人设/语气/风格）
2. 读取 knowledge-base/README.md（总览入口）
3. 按 references/dy-knowledge-base.md 检索历史同类记录
4. 确认浏览器 profile="openclaw" 可用（openclaw browser start --browser-profile openclaw）
5. 按 references/dy-openclaw-browser-guide.md 确认 CLI 命令语法和交互模型
6. 注入指纹隐藏脚本（about:blank → openclaw browser evaluate 注入 → 自检）
7. 检查账号健康度
8. 按 SKILL.md 中对应章节执行具体任务
9. 任务中/后按规则沉淀知识库
```

## 十、设计决策总结

### 10.1 为什么沿用小红书技能架构

小红书技能已验证了"文档驱动 + 主框架 + 引用文件 + 知识库"的架构有效。抖音作为同类型短视频平台，运营链路高度相似（定位→选题→生产→发布→复盘），可以复用同一架构，降低维护成本。

### 10.2 为什么将完播率设为核心指标

抖音推荐算法以完播率为核心权重。内容能否被推荐，完播率比点赞数更重要。因此技能在选题、分析、追踪、复盘各环节都将完播率作为第一优先级指标。

### 10.3 为什么增加前3秒钩子设计

抖音用户的滑动决策在前3秒内完成。如果前3秒留不住人，完播率必然低，推荐量级也上不去。因此选题阶段就要求设计前3秒钩子方案，从源头解决留存问题。

### 10.4 为什么人设从"傲娇嘴硬"改为"直球带梗"

抖音用户群体和平台氛围比小红书更直接、更娱乐化。"傲娇嘴硬"的风格适合小红书的图文社区氛围，而抖音需要更快节奏、更直接的表选方式。"直球带梗"既保持了人设辨识度，又更符合抖音用户的阅读习惯。

### 10.5 为什么使用 data-e2e 作为主 selector

抖音 Web 端大量使用 `data-e2e` 属性标记元素，这些属性比 class 名更稳定（class 名经常因编译哈希变化），作为 selector 可减少页面改版导致的维护成本。

### 10.6 为什么视频上传期间禁止其他操作

视频文件通常较大，上传过程消耗浏览器资源。如果在上传期间操作其他页面元素，可能导致浏览器卡顿、上传中断或页面崩溃。因此技能明确规定上传期间不做其他操作。

### 10.7 为什么统一 CLI 命令语法到 dy-openclaw-browser-guide.md

OpenClaw 的 CLI 命令语法与通用 Playwright/Puppeteer 命令有差异（如 `browser start --profile` vs `openclaw browser start --browser-profile`、无 `browser upload` 和 `browser wait` 命令等）。技能初期文件中混用了旧版命令语法，导致实际执行时频繁报错。通过创建 `dy-openclaw-browser-guide.md` 统一所有命令语法、交互模型（snapshot→ref→act）和文件上传机制，其他文件只需引用该规范，避免散落维护和语法不一致。

## 十一、术语表

| 术语 | 定义 |
| --- | --- |
| 选题 | 可发布、可讨论、可转发的内容切入点 |
| 引流钩子 | 视频/标题/封面用于触发停留与完播 |
| 结构化输出 | 标题、文案/脚本、互动问句、话题、标签五元组 |
| 快照 | 用于验证页面状态的关键证据（`openclaw browser snapshot` 返回的 UI 树） |
| 回放 | 流程失败后重试或改道执行 |
| Viral Copy | 输入爆款 URL，高贴合学习后生成近似结构内容的链路 |
| Source Template | 从源视频拆解出的结构化模板 |
| 半程预发 | 视频已上传 + 封面已选 + 标题文案已填 + 停在发布按钮处未点击 |
| pattern | 知识库中可复用的爆款结构、互动钩子等模式记录 |
| evaluate | `openclaw browser evaluate`，使用 JS 在浏览器页面内批量提取结构化字段的操作 |
| snapshot | `openclaw browser snapshot`，获取页面 UI 树文本结构和元素 ref |
| ref | OpenClaw snapshot 返回的元素引用标识，用于 `act` 操作 |
| act | `openclaw browser act`，基于 ref 执行点击/输入等交互动作 |
| one-send-per-turn | 每轮只发送 1 条回复的默认风控策略 |
| 完播率 | 视频被完整观看的比例，抖音推荐算法核心指标 |
| 黄金3秒 | 视频前3秒决定用户是否划走，是内容成败关键 |
| Dou+ | 抖音官方加热工具，付费推广内容 |
| 星图 | 抖音达人营销平台，用于商单对接 |
| evaluateEnabled | OpenClaw 配置项，需为 true 才能 `openclaw browser evaluate` |
| SSRF Policy | OpenClaw 的 SSRF 防护策略，需确保目标域名在允许列表 |
