# 豆蜂 WorkBuddy 版设计说明

## 架构

豆蜂由四部分组成：

1. **Buddy 应用**：提供账号策略、内容创作、发布复盘三种工作模式和七个高频场景。
2. **运营 Skill**：定义抖音运营方法、输出格式、工具选择和确认规则。
3. **MCP Connector**：提供工作区设置、诊断、研究、选题、发布清单、评论草稿、效果数据、知识检索和回采计划工具。
4. **腾讯 BrowserSkill**：使用用户已登录的 Chrome 或 Edge 完成网页读取和受控交互。

可视化工作台继续作为人工编辑、检查和数据回看界面。网页和 MCP 共用 `runtime/workbench.json`。

## 设计原则

- AI 生成由 WorkBuddy 模型负责，项目不绑定单独模型供应商。
- 业务数据通过 MCP 工具结构化读写，便于 WorkBuddy 正确选择工具。
- 浏览器只使用 BrowserSkill，不自行维护登录凭证。
- 读取可自动执行；发布、评论发送、点赞、关注、删除和资料修改执行前必须确认。
- 遇到验证码、频率限制或账号异常时停止，不尝试绕过平台限制。
- 参考内容只拆解主题、结构和互动机制，成稿必须原创。

## 数据流

```text
用户 ↔ WorkBuddy Buddy 应用
             ├─ douyin-ops Skill
             ├─ 豆蜂 MCP Connector ↔ runtime/workbench.json
             └─ BrowserSkill ↔ 用户浏览器 ↔ 抖音/创作者中心

用户 ↔ public/ 可视化工作台 ↔ server/server.mjs ↔ runtime/workbench.json
```

根目录 `server.mjs` 保留为启动入口，导入 `server/server.mjs`。前端页面在 `public/`，后台业务在 `server/`，发布队列共用模型在 `shared/`。网页依赖的工作区模型仍位于 `workbuddy/connector/lib/`，以支持 MCP 能力包独立分发。静态资源使用明确的 URL 映射，既有页面地址无需修改。

## 发布边界

本地代码和 WorkBuddy 能力包已经准备完成。正式上架还需要在 WorkBuddy 开放平台创建应用，取得平台生成的应用 ID，完成预览与审核。该步骤依赖用户的开发者账号。
